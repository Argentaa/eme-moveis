**Goal:** permitir N cards por cliente no funil de vendas. Hoje o card É o cliente (`clients.funnel_id/funnel_status/...` — 1 linha = 1 card), por isso cliente com venda concluída caía no limbo (caso Elisandra, out/2026) e o "Vincular" só listava quem estava fora do funil.

**Architecture:** nova entidade `deals` (Negociação). `clients` vira só cadastro (contato, cpf, endereço, flags de fornecedor); cada `deal` é um card (`client_id` + `funnel_id` + `funnel_status` + valores + flags de conclusão + vendedor/parceiro). `sales` e `projects` ganham `deal_id` opcional. Relatórios/metas/comissões passam a ler `deals`+`sales` (mesma base unificada do fix `a36b738`, só troca a tabela de origem das flags).

## 2. Decisões de design (revisar com o dono — a nº 1 muda números passados)

1. **Comissões passam a contar `Sale.total_value` por `sale_date` (igual ao planejamento), não mais `estimated_value` por `closed_at`.** Efeito medido no dry-run: outubro/2026 daria **R$ 9.695 (novo) vs R$ 40.000 (antigo)** — o antigo somava estimativas (e zerava Elisandra/Gustavo, sem estimado). O novo é o valor real vendido; o planejamento (`goals_bp`) já usa essa base, então meta e comissão voltam a contar a mesma história. **Gate: o dono precisa aceitar a reexpressão dos meses passados.**
2. **Nome da tabela: `deals`.** (O plano de 06/10 sugeria `crm_opportunities`; `deals` segue o padrão curto das demais — `sales`, `projects`, `clients`.)
3. **Backfill 1:1:** cada cliente COM funil gera 1 deal ("Negociação inicial — {nome}") copiando `funnel_id/status/estimated/lost_reason/seller/partner/lead/campaign/flags`. Cliente sem funil não gera deal. Histórico preservado por construção — nenhuma linha de `clients` é alterada pela migração.
4. **`sales.deal_id` / `projects.deal_id`:** preenchidos pelo `client_id` (nesta fase há 1 deal por cliente — ligação unívoca). `interactions` e `negotiation_items` **continuam no cliente** (são histórico do cadastro, não da negociação) — evita migração destrutiva e o detalhe do cliente segue mostrando tudo.
5. **Compatibilidade:** `clients.funnel_*` **não são removidos** nesta entrega (leitura dupla + escrita espelhada no deal principal). Remoção vira Fase E, depois de 1 ciclo de uso validado. Rollback = voltar o deploy; os dados antigos continuam lá.
6. **NÃO duplicar ficha de cliente** para simular 2 cards (quebra `cpf_cnpj` único, divide financeiro/histórico, suja o central). Foi avaliado e rejeitado.

## 3. Migração 0036 — spec (padrão idempotente do repo, inspector + `IF NOT EXISTS`)

`erp-backend/alembic/versions/0036_deals.py` (revision `0036_deals`, down `0035_sale`):

- `deals`: `id` String(36) PK · `client_id` FK clients CASCADE NOT NULL, index · `funnel_id` FK funnels SET NULL, index · `funnel_status` String(60) NOT NULL default `PROSPECCAO` · `title` String(200) NOT NULL default `''` · `estimated_value` Numeric(14,2) · `lost_reason` Text · `seller_id` FK users SET NULL · `partner_id` FK partners SET NULL · `lead_source`/`campaign` String(120) default `''` · `sale_concluded_at`/`closed_at` DateTime, index em `closed_at` · `created_at` DateTime NOT NULL.
- `sales.deal_id` / `projects.deal_id`: `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` **sem constraint FK no banco** (padrão 0011 do repo — FK só no modelo; SQLite/pytest com foreign_keys OFF).
- Backfill em Python (não SQL puro): 1 deal por cliente com `funnel_id` sem deal naquele funil; depois liga sales/projects pelo `client_id`. Re-run = no-op (guardado por `NOT EXISTS`).
- Validação local: PG temporário (`postgres:16-alpine` na 5499) + `alembic upgrade head` + re-run no-op + derrubar container.
